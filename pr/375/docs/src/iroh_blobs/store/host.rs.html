1//! The store host: the generic part of a store, which a backend plugs into.
2//!
3//! The host is one opinionated way to build a store, not the only one. Anything
4//! that answers [`crate::api::proto::Request`] is a store. You can implement
5//! the protocol yourself and wrap it with
6//! [`Store::from_client`](crate::api::Store::from_client), or wrap another
7//! store and forward what you don't handle. That is the better choice for a
8//! store that only serves part of the protocol, or works very differently.
9//!
10//! The host does everything that is the same for every store: routing requests
11//! by hash, temp tags, gc sessions, imports, and the order of operations between
12//! handlers and the metadata store. The backend decides how entries are stored.
13//! You start a store with [`start`] and use it through the irpc client it
14//! returns, like any other store.
15//!
16//! # Handlers
17//!
18//! The most useful part of the host is how it runs handlers. Every request for a
19//! hash goes to that hash's handler, and runs as a task on the handler's own
20//! actor. Tasks of one handler are concurrent, but only interleave at `.await`
21//! points, so the handler is the single place that decides about its hash. The
22//! host creates handlers on demand, keeps them alive while they have tasks, and
23//! recycles idle ones for other hashes, allocations included.
24//!
25//! # Building a backend
26//!
27//! You implement [`Backend`], which names the handler type and starts the
28//! metadata store, and [`HashHandler`], which has one async method per request.
29//! The metadata store answers the [`metadata`] protocol, with whatever storage
30//! you like.
31//!
32//! Two optional helpers do most of the work of a handler. [`StateCell`] handles
33//! the lifecycle of an entry: loading, writes behind a [`WriteGuard`], freezes,
34//! deletes and observers. You only define the loaded state. [`bao::BaoAccess`]
35//! gives you bao import and export, if your reads are synchronous.
36//!
37//! Data outside the store is named by a [`Location`], bytes that only the
38//! backend interprets. The fs backend keeps a path there.
39//!
40//! # Design
41//!
42//! The metadata store owns the metadata, each handler the data of its hash. A
43//! handler's state is a cache of its entry, valid because the handler is the
44//! only writer. Entries only grow. A delete is the one exception, so it goes through
45//! the handler as well.
46//!
47//! Besides running the handlers, the store actor holds the temp tags and forwards
48//! everything else to the metadata store. The metadata store never touches
49//! entry data, except for recovery when the store opens. All its senders share
50//! one channel, so it sees requests in the order they were sent.
51//!
52//! # Metadata
53//!
54//! A handler talks to the metadata store through `EntryMeta`:
55//!
56//! | Method | Waits | Meaning |
57//! |---|---|---|
58//! | `get()` | for the reply | get the entry state |
59//! | `set(state)` | until applied | replace the entry state |
60//! | `update(state)` | no | merge into the entry state |
61//! | `update_await(state)` | until applied | merge into the entry state |
62//! | `delete()` | until committed | ensure the entry is absent |
63//!
64//! Applied means visible to later requests, not durable. Only `delete()` waits
65//! for the commit, since the handler removes the data right after.
66//!
67//! After a commit, the metadata store reports parts that a hash no longer
68//! references. That doesn't make them garbage, since the handler may still use
69//! them. So the store actor hands them to the hash's handler, waking one if
70//! needed, and the handler decides from its loaded state.
71//!
72//! # Deletes
73//!
74//! The store actor sends each delete to the hash's handler, so it is ordered with
75//! everything else for that hash. A delete that is not forced skips content with
76//! a temp tag. The handler starts a new generation, which ends observers, deletes
77//! the entry, waits for the commit, and then removes the data.
78//!
79//! A metadata error aborts the whole store. There is no rollback.
80//!
81//! # GC sessions
82//!
83//! `GcRun` opens an exclusive session. The store sends a snapshot of candidates
84//! and roots, gc sends back its sweep deletes, and closing the channel ends the
85//! session. While it lasts, the store holds back all tag changes, including temp
86//! tag creation and import completion, and queues them until the end.
87//!
88//! Before sending the snapshot, the store freezes every HashSeq root. A frozen
89//! entry can be read, but writes and deletes wait. So no new reference can show
90//! up between traversal and sweep, and blobs added after the snapshot are never
91//! swept.
92//!
93//! The protect callback runs while the session is held. It must not wait for
94//! anything the session holds back, or the gc run deadlocks. External systems
95//! must protect content before they publish references to it. A tag does not
96//! bring back data that gc already deleted.
97//!
98//! # Tasks
99//!
100//! Tasks don't return a result; they send errors to the requester themselves.
101//! Usually an impl fn returns a result, so it can use `?`, and a thin `..._task`
102//! wrapper forwards the error.
